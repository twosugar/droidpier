| Браузер | Поддерживается |
|---|---|
| Google Chrome | Да |
| Microsoft Edge | Да |
| Safari | Нет |
| Firefox | Нет |

Измерения на странице [требований](/ru/docs/getting-started/requirements/#measured-performance) проводились в Chrome 157.

## Почему не работает Safari

Страница отдаётся по `https` и подключается к шлюзу на вашем Mac через `ws://127.0.0.1` (или `ws://localhost`), которое не шифруется. Safari считает это смешанным содержимым (незащищённое подключение с защищённой страницы) и блокирует его. В Safari страница не может связаться со шлюзом.

## Firefox

Firefox не поддерживается.

## Как страница проверяет браузер

<!-- verify: phase 3 -->
Страница читает `navigator.userAgentData.brands`. Она продолжает работу, только если в списке есть `Google Chrome` или `Microsoft Edge`. В противном случае она просит открыть страницу в Chrome или Edge и не пытается подключиться.

<!-- verify: phase 3 -->
Safari и Firefox не предоставляют `navigator.userAgentData`, поэтому они отклоняются. Другие браузеры на базе Chromium, которые не сообщают бренд Chrome или Edge, тоже отклоняются.

## Доступ к локальной сети в Chrome

<!-- verify: phase 3 -->
- Начиная с Chrome 147, публичная страница по `https`, которая подключается к `localhost`, сначала должна получить разрешение пользователя. Chrome спрашивает один раз и запоминает ответ для сайта.
- Начиная с Chrome 154, страница может указать, что подключается к loopback-адресу (`targetAddressSpace: "loopback"` при открытии WebSocket). Страница так и делает, а в версиях, которые не поддерживают этот параметр, использует обычный WebSocket.
- Начиная с Chrome 156, корпоративные политики больше не могут отключить эту проверку.

Если вы отказали в разрешении, см. [Устранение неполадок](/ru/docs/guides/troubleshooting/#chrome-blocked-local-network-access).
