# Contributing Guide

Contributions are welcome. If you find a bug or have an idea, please open an issue or submit a pull request.

Please write clean code that follows the style and organization of the existing code, and make sure all tests pass.

Please submit **one PR that does one thing**. It makes your change easier to review and faster to merge.

Before writing code, read [AGENTS.md](AGENTS.md) (the project rules, commands and conventions), [CONTEXT.md](CONTEXT.md)
(the names of things) and, for a larger change, the design spec in `docs/superpowers/specs/`.

## What Droidpier is, and is not

Droidpier replaces the Android Studio emulator window with a page in Chrome or Edge. The emulator itself stays the
official one, unmodified, running on the user's own Mac. These are decisions, not gaps waiting to be filled:

- No emulator of our own, no patched emulator, no dependence on Android Studio running.
- No emulators on a server, no sharing one emulator between people: the public page is static, and nothing about the
  user's device leaves their Mac.
- One device at a time.
- Chrome and Edge only (they support the local network access the page needs). Safari and Firefox are not supported.
- Apple Silicon Macs first. Intel Macs and Windows are planned, so platform-specific code stays in
  `gateway/src/platform.ts`.

Features specific to one business are out of scope, with one exception the project chose to include: inspecting H5
pages in apps and pointing them at a local dev server.

A change is judged by how it feels next to the Android Studio emulator and scrcpy: it must not add visible latency
or keep the Mac busy while the page is idle.

## AI-Assisted Contributions

Droidpier fully embraces AI-assisted development. We welcome contributions written with AI, including pull requests
where 100% of the code was generated by AI.

What matters is not who wrote the code, but whether the change is thoughtful, focused, and well validated. The
contributor is always responsible for the final result.

Before opening a pull request, please make sure that:

- The problem is real and the change is necessary. For a bug, say how to reproduce it and what the cause is.
- The implementation follows the existing patterns of Droidpier and the rules in [AGENTS.md](AGENTS.md).
- The code has been reviewed by you and properly tested: unit tests for the behavior, and a run against a real
  emulator for anything that touches the emulator, adb or the page (screenshots are encouraged for UI changes).
- A pull request focuses on one thing and keeps the diff as small as practical. When using AI, ask it to avoid
  unrelated refactors, cleanup, or formatting. **Less is better.**

### Describe protocol and command line changes

The public page and each user's gateway are updated separately, so a change to how they talk is a change to a
public contract. A pull request that adds, changes or removes a WebSocket message, a field, a close code, a
`host.call("emu.*")` function or a `droidpier` flag lists it in the description under `## Protocol`, with one line on
what it is for, and says whether `PROTOCOL_VERSION` changed and why. A page and a gateway of different protocol versions
refuse to work together until the user updates one of them, so the version moves only when an older page or gateway
cannot work with the change.

Issues are always welcome, but when practical, we encourage you to try a fix and open a pull request. Concrete code
often communicates a problem more efficiently than a long discussion. A pull request is still subject to review and
is not a guarantee that the proposed change will be accepted.

## Commits and pull requests

Commit subjects and pull request titles name the area first, then say what changed as an imperative sentence:

```
<area>: <What the change does>
```

- The area is the part of Droidpier the change is about, in lower case: `gateway`, `host` (the host module), `ui`
  (the page), `protocol` (`shared/protocol.ts` and what both sides do with it), `install` (the install script and
  first-run installs), `build` (binaries and the Pages deploy directory), `docs`, `spike`. Name one area only, never
  several separated by commas: when a change spans several, look at it as a whole and name the part it is mostly
  about.
- The sentence starts with a capital letter, uses the imperative mood, has no trailing period and fits in about 72
  characters with its area. It says what the change does for a user of Droidpier, not which files moved:
  `gateway: Match running emulators by AVD id, not display name`, not `gateway: Update discovery.ts`.
- Do not use conventional prefixes (`fix:`, `feat:`, `chore:`).
- The body (optional for small changes) explains why, wrapped at 72 columns: the problem, the cause, the approach and
  what it costs.

Examples:

```
gateway: Match running emulators by AVD id, not display name
gateway: Show why the emulator exited during boot
ui: Rotate the whole device frame
host: Free the upload slot when the page gives up
install: Update and start droidpier with one command
docs: Describe deploying the public page
```

## Development and Testing

### System dependencies

- An Apple Silicon Mac with the Android SDK (`ANDROID_HOME`, or `~/Library/Android/sdk`) and at least one arm64 AVD.
  The page's first-run guide can install the SDK pieces for you.
- Node 22.6 or later (it runs the TypeScript sources directly).
- pnpm 8 for dependencies (the lockfile is pnpm 8's): `npx pnpm@8 install --frozen-lockfile`.
- [Bun](https://bun.sh) for bundling the host module and the gateway binary.
- To build the page: the [nsh](https://github.com/longbridge/nsh) toolchain (`NSH=/path/to/nsh`, or `nsh` on the
  `PATH`) and LLVM (`/opt/homebrew/opt/llvm/bin`, or set `LLVM_BIN`).
- Chrome or Edge.

### Checks

Run these before opening a pull request (the commands are in [AGENTS.md](AGENTS.md)):

```sh
npm test                                              # unit tests, gateway and shared
EMU_IT=1 node --test gateway/test/emulator.it.test.ts # with an emulator running, for emulator-facing changes
```

### Run it

```sh
npm start                                       # the gateway from source on port 7300
node gateway/src/main.ts --port 7306 --no-open  # alongside an installed droidpier, on another port
```

Open `https://droid.devpier.dev/app/` (or `#port=<port>` for another port) in Chrome. To try page or host module
changes, build them (`bun run build:host`, `NSH=/path/to/nsh bun run build:ui`) and open the gateway's local page
with `--local`.

On macOS the gateway takes WebSocket connections only from Chrome and Edge processes, and nothing from the
emulator or adb. To drive it from a script (for example `spike/lifecycle-ws.ts`), start that gateway with
`DROIDPIER_ALLOW_ANY_WS_CLIENT=1`. Use it for tests and scripts only.

### Reviewing changes

Check whether the tests and the description cover the behavior the pull request claims, including its states: an
emulator booting, running, rebooting, closed outside Droidpier, adb not answering; the page and the gateway on
different versions; an AVD whose display name differs from its id. Ask for a manual check only for what tests cannot
exercise, and name the scenario.
